# GlowESP — исследовательская версия 0.3

В версиях 0.1–0.2 найден неверный 32-битный тип GC handle для Unity 6000, вызывающий падение при обращении к удержанным объектам. Использовать только сборки 0.3 и новее. В 0.3 чтение удержанных объектов и первой страницы каталога проверено на настоящем клиенте; скинченджер ещё не завершён.

**Это исследовательский модуль. GitHub Actions собирает arm64 framework; устанавливаемый IPA и сертификаты в репозиторий не входят.**

Целевое устройство: iPhone 13 без джейлбрейка. Подключённый по USB телефон сообщает iOS 26.3; первоначально пользователь указал 26.6. Проверка игрового адаптера на этом устройстве ещё не завершена.

## Что реализовано в исходниках

- Простое меню: двойное касание тремя пальцами открывает и закрывает его. Плавающей кнопки нет, по умолчанию меню скрыто. Жест добавляется в окно игры без отмены её касаний. Системные жесты универсального доступа могут конфликтовать; на физическом телефоне жест ещё не проверен.
- UIKit overlay с пропуском касаний вне меню, safe area, прокруткой и поддержкой сценового и старого жизненного цикла Unity.
- Угловые / полные рамки, мягкое мятное свечение, подписи расстояния, прозрачное меню.
- Адаптер через экспортированные IL2CPP API, выбор перегрузок по точным типам параметров, проверка наследования `PlayerBindings` от `Component`, удержание объектов через GC handles.
- Экспериментальная тонировка копий материалов с восстановлением оригиналов при выключении, уходе приложения в фон и обновлении списка. Это не подтверждённые чамсы сквозь стены.
- Защита при обнаружении записи / трансляции: скрывает всё окно меню и ESP, приостанавливает выборку целей, восстанавливает материалы. Эффекты исчезают также с экрана телефона. Все новые визуальные функции должны проходить через `Runtime::setVisualsAllowed` и иметь восстановление состояния в `restore()`.
- Скрипт сборки framework на Mac с Xcode; скрипт упаковки для Windows, который сохраняет исходный IPA и проверяет запас места в Mach-O header перед добавлением load command.

## Чего пока нет

- Подтверждённого подключения к игровым сущностям на устройстве. `PlayerBindings` найден в метаданных, но его пригодность для поиска объектов проверяется только при запуске. При несовпадении адаптер прекращает работу с диагностикой.
- Различения союзник / противник, здоровья, имён и костей. Рамки относятся к кандидатам `PlayerBindings`, а не к подтверждённым противникам.
- Надёжных чамсов сквозь стены. Тонировка зависит от доступности `_Color` у материала.
- Полноценного stream-proof: отдельное изображение для записи при сохранении эффектов на телефоне не реализовано. Защита срабатывает после уведомления / обновления статуса захвата и не гарантирует отсутствие переходных кадров. Одиночные скриншоты, внешняя камера и нестандартные способы захвата не покрываются.
- Скинченджера: игровые методы применения внешнего вида, их аргументы и жизненный цикл оружия не установлены. Изменение серверного инвентаря не реализовано.
- Проверки установки и игровой работы на целевом телефоне. Совместимость iOS 26.6, подписи и игровых проверок не подтверждена.
- Каких-либо гарантий необнаружения или обхода античита.

## Основание анализа

Исходный расшифрованный IPA: `com.axlebolt.standoff2_1.1.0.decrypted.ipa`, 1 936 976 316 байт.

- Bundle ID `com.axlebolt.standoff2`, версия 1.1.0, сборка 176383.2.
- Unity `6000.3.13f1`; metadata v39; 36 001 определение типа.
- В UnityFramework подтверждён `cryptid = 0`; привязка экспортов IL2CPP проверяет наличие каждого API перед работой.
- Начальный запуск Cpp2IL остановился на `Failed to find pCodegenModules`. После исправления ограничения поиска в исследовательской копии анализатора таблицы регистрации найдены и сопоставлены 196 673 определения методов с нативными указателями. Подробнее: `analysis/skin-research.md`.
- Подтверждено наследование `PlayerBindings` от `UnityEngine.MonoBehaviour`. Наличие нужных экземпляров в матче и соответствие рамок персонажам ещё не проверялись на телефоне.
- Названия части классов и методов обфусцированы.

Сырые метаданные, таблицы символов и бинарники игры хранятся только локально и не публикуются в репозитории. Их адреса не используются как игровые офсеты.

## Сборка и упаковка

В [Actions](https://github.com/kup3r/standoff_module/actions/workflows/build-ios.yml) сборка запускается при push в main, pull request или вручную через Run workflow. Задание build использует macOS и iPhoneOS SDK; package-tests проверяет упаковку на Windows. В артефакте — `GlowESP.framework.zip` и SHA256SUMS. Framework подписан ad hoc для проверки структуры, перед установкой его нужно переподписать вместе с приложением.

На Mac с установленным Xcode и iPhoneOS SDK:

```sh
bash build-macos.sh
```

Результат: `build/GlowESP.framework`. Наличие исходников само по себе не позволяет запустить модуль на телефоне.

На Windows после переноса собранного framework:

```powershell
.\package-windows.ps1 -SourceIPA 'C:\path\game.decrypted.ipa' -FrameworkDirectory 'C:\path\GlowESP.framework' -OutputIPA 'C:\path\game.glow.unsigned.ipa'
```

Этот шаг добавляет framework и `LC_LOAD_DYLIB`. Исходные подписи после изменений недействительны. Требуется переподпись всего приложения и вложенного framework средствами, поддерживающими твою iOS и профиль. Сертификаты в пакет не включены. Упаковка проверена с настоящим framework: тело исполняемого файла вне таблицы команд сохранено, размер и CRC 2 541 остальных исходных записей совпадают, встроенный framework побайтно совпадает с артефактом Actions.

Для доступа к файловому мосту разработки по USB используется отдельный `GlowESP.dev.framework.zip`. Подготовить Info.plist можно командой `python tools/diagnostic-info.py game.decrypted.ipa development.plist`, затем передать `-DevelopmentInfoPlist development.plist` скрипту упаковки. Меняются только `UIFileSharingEnabled` и `LSSupportsOpeningDocumentsInPlace`; стандартный вариант доступа к документам не добавляет. Файловый мост обрабатывается, пока игра активна на экране.

USB-клиент: `python -m pip install pymobiledevice3==11.52.1`, затем `python tools/usb-diagnostics.py roots`. Телефон должен быть разблокирован, доверять ПК и показывать диагностическую игру. Найденный ID массива с ролью `publicCosmeticCatalogue` передаётся в `python tools/usb-diagnostics.py catalogue ID`. Выходные JSON сохраняются локально в `diagnostics/`; публиковать содержимое личных игровых контейнеров не нужно. Клиент ожидает iPhone 13 по USB и сборку Standoff с доступом к документам. Команды читают созданные объекты и публичные определения, не выдают предметы и не выполняют произвольный код.

## Первый запуск и проверка

1. Открыть переподписанное приложение и дважды коснуться экрана тремя пальцами. Меню должно появиться, повторный жест или «Закрыть» его скроют.
2. Войти в тренировочный / собственный матч, открыть меню, включить ESP.
3. Прочитать диагностику адаптера. Если `PlayerBindings is not a Component`, нужен другой подтверждённый игровой тип; менять адреса наугад не следует.
4. Сверить рамки с персонажами; отдельно проверить камеру, смену сторон и смену сцены. Только после этого можно считать адаптер функциональным.
5. Тонировку проверять отдельно; убедиться, что выключение и уход в фон возвращают исходные материалы.

При отсутствии камеры или необходимого класса адаптер не рисует цели. Здоровье и команды не имитируются.

## Проверка захвата

При уже включённых ESP и тонировке запустить штатную запись экрана: меню и рамки должны исчезнуть, материалы — восстановиться. На телефоне эффекты тоже отключаются. После окончания записи выбор настроек сохраняется, тонировка восстанавливается при очередной выборке. До проверки записи на iPhone 13 нельзя считать защиту подтверждённой. Тест Simulator проверяет запуск окна и меню, конфигурацию жеста, маршрутизацию касаний и скрытие при уходе из активного состояния; реальную запись он не проверяет.

## Скинченджер: результат исследования

В метаданных подтверждены `Axlebolt.Standoff.Gameplay.WeaponMeta.WeaponMetaData` с `SkinId`, `SkinPatternId`, `CharmId` и `StickerMetaData`, а также `PlayerAnimationData.WeaponSkinId`. Это поля данных; не подтверждены активный владелец, получение локального оружия, загрузка нужных ресурсов и метод обновления модели. Рабочий скинченджер не добавлен: запись в случайный объект с полем `SkinId` не является сменой скина и может затронуть сетевые данные.
